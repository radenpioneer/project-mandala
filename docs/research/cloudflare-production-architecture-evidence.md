# Cloudflare production architecture evidence

_Research date: 14 August 2026_

## Scope and confidence

This note records decision-relevant facts for **Choose production architecture and data boundaries**. It uses current official Cloudflare documentation only. It does not select the product architecture, define product policy, or replace a threat model, privacy assessment, load test, or recovery rehearsal.

The evidence is strongest for platform behavior and documented limits. It is weaker where Cloudflare does not publish a delivery guarantee—for example, the documentation reviewed does not state an exactly-once guarantee or a complete retry schedule for Cron Triggers. Those gaps are called out rather than filled by assumption.

## Workers, Static Assets, and releases

- Workers Static Assets can deploy the frontend and Worker code together. By default, a matching asset is served before the Worker runs; a missing asset falls through to the Worker. `assets.run_worker_first` can instead run the Worker for every request or only selected patterns such as `/api/*`. An `ASSETS` binding lets Worker code fetch an asset explicitly. Sources: [Static Assets](https://developers.cloudflare.com/workers/static-assets/), [Worker script routing](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/), and [asset configuration](https://developers.cloudflare.com/workers/static-assets/binding/).
- A Worker **version** captures bundled code, static assets, bindings, and compatibility settings. It does **not** capture state changes inside D1, KV, R2, or Durable Objects. A deployment may serve one version or split traffic across two versions. Uploading can be separated from promotion, and each uploaded version can receive a preview URL. Sources: [Versions and deployments](https://developers.cloudflare.com/workers/versions-and-deployments/) and [Preview URLs](https://developers.cloudflare.com/workers/versions-and-deployments/preview-urls/).
- Preview URLs are public unless protected with Cloudflare Access, and Workers Logs, `wrangler tail`, and Logpush are not available for preview URLs. This limits their value for production-like observability tests. Source: [Preview URL rules and limitations](https://developers.cloudflare.com/workers/versions-and-deployments/preview-urls/).
- A rollback immediately makes the selected version active, but it does not roll back connected storage. Old code can fail against a changed schema, and deletion or incompatible modification of bound resources can prevent a rollback. Only the 100 most recently published versions are rollback candidates. Source: [Rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/).
- Gradual deployments route requests independently by default. This can create API contract skew and can break content-hashed static assets when HTML comes from one version and an asset request reaches another. Version affinity can pin a stable key to one version for the duration of the deployment. Sources: [Gradual deployments](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/) and [Version affinity](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/version-affinity/).
- Current Static Assets limits are 20,000 files per version on Workers Free and 100,000 on Workers Paid, with a 25 MiB per-file limit on both. Source: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#static-assets).

**Decision consequence (inference):** an application rollback and a database rollback are separate operational acts. Any release procedure that changes D1 schema needs backward-compatible migration rules or an explicit coordinated recovery procedure; platform version rollback alone is not a data rollback.

## D1 data and transactional boundaries

### Access and atomicity

- A Worker accesses D1 through an environment binding such as `env.DB`; the binding name is declared in Wrangler configuration. Bindings are capabilities as well as APIs, so Cloudflare-managed resources do not require application-level API credentials. Sources: [D1 Workers Binding API](https://developers.cloudflare.com/d1/worker-api/) and [Workers bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/).
- D1 otherwise operates in auto-commit. `D1Database.batch()` executes its prepared statements sequentially and non-concurrently as one SQL transaction; if one statement fails, the whole sequence aborts or rolls back. Source: [`D1Database.batch()`](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch).
- Each D1 database is single-threaded and processes one query at a time. Excess concurrency is queued until the queue fills, after which D1 returns an overloaded error. Current per-database size is 500 MB on Free and 10 GB on Paid; the 10 GB database limit cannot be raised. A Worker invocation may issue 50 D1 queries on Free or 1,000 on Paid and may open at most six simultaneous D1 connections. Source: [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
- D1 automatically retries a retryable read-only query up to two additional times. Application-level write retries are safe only when the business operation is idempotent; Cloudflare recommends backoff with jitter for retryable failures. Sources: [Retry queries](https://developers.cloudflare.com/d1/best-practices/retry-queries/) and [D1 error guidance](https://developers.cloudflare.com/d1/observability/debug-d1/).

### Location and read consistency

- Without an explicit setting, D1 chooses a primary location near where the database-creation request originated. An `apac` location hint is available, but a hint is not a residency guarantee: D1 uses the nearest possible supported location by latency. The only documented jurisdiction constraints are `eu` and `fedramp`, and a jurisdiction can be set only when the database is created. Source: [D1 data location](https://developers.cloudflare.com/d1/configuration/data-location/).
- Without read replication, all reads and writes go to the primary. With read replication, replicas are asynchronous and may be arbitrarily behind; all writes still go to the primary. The Sessions API supplies sequential consistency, `first-primary` starts from the latest primary state, and a bookmark carries a minimum observed version into a later session. Sessions are available only through a D1 Worker binding, not the REST API. Source: [D1 global read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/).

**Decision consequence (inference):** `apac` does not establish Indonesian data residency. Whether Cloudflare's documented location behavior satisfies the project's legal and privacy constraints remains a human/legal decision. If read replication is enabled, any read-after-write path needs an explicit Sessions/bookmark policy; “replicated” must not be treated as “immediately current.”

### Backup and restore

- Time Travel is always enabled on production-backend D1 databases. It provides minute-level point-in-time recovery for 7 days on Free and 30 days on Paid without a scheduled backup job. Source: [Time Travel and backups](https://developers.cloudflare.com/d1/reference/time-travel/) and [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
- Restore overwrites the database in place and cancels in-flight queries and transactions. The returned bookmark permits an undo restore, but Time Travel still cannot clone or fork a database. Source: [Restore a D1 database](https://developers.cloudflare.com/d1/reference/time-travel/#restore-a-database).
- Cloudflare documents exporting D1 to R2 via the REST API and Workflows only as an option for retaining a database state longer than the Time Travel window. Source: [Export D1 into R2](https://developers.cloudflare.com/d1/reference/time-travel/#export-d1-into-r2-using-workflows).

## Queues and scheduling

- Queues provides **at-least-once**, not exactly-once, delivery; a message may be delivered more than once and ordering is not guaranteed. Cloudflare recommends a producer-generated unique ID used as a database primary key or downstream idempotency key when duplicate processing would be harmful. Sources: [Delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) and [How Queues works](https://developers.cloudflare.com/queues/reference/how-queues-works/).
- A successful consumer return acknowledges a batch. Individual `ack()` calls prevent already-processed messages from being redelivered if a later message fails. Otherwise, one failure causes the entire batch to be retried. The default is three retries; after the limit, a message is deleted unless a dead-letter queue is configured, in which case it is written there. Source: [Batching, retries, and delays](https://developers.cloudflare.com/queues/configuration/batching-retries/).
- A message or retry can be delayed by no more than 24 hours. Retention is configurable up to 14 days (Free is fixed at 24 hours); messages that reach retention are deleted. Other current ceilings include 128 KB per message, 100 messages per consumer batch, 5,000 messages/second per queue, and 15 minutes wall time per consumer invocation. Source: [Queues limits](https://developers.cloudflare.com/queues/platform/limits/) and [Queues pricing/retention tiers](https://developers.cloudflare.com/queues/platform/pricing/).
- Cron Triggers invoke a Worker's `scheduled()` handler using UTC cron expressions. Trigger configuration changes can take up to 15 minutes to propagate. A scheduled invocation has a 15-minute wall-time ceiling; the 100 most recent events are visible in Cron Events, while Workers Logs can retain events longer. Sources: [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/) and [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#wall-time-limits-by-invocation-type).
- The Cron documentation records the handler/waited-promise outcome and exposes `controller.noRetry()`, but the reviewed documentation does not state an exactly-once delivery guarantee or a complete retry timing contract. Source: [Scheduled handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/).

**Decision consequence (inference):** a Queues consumer needs durable idempotency, per-message acknowledgement, bounded retries, and an explicit DLQ inspection/replay procedure. A periodic Cron handler should also be idempotent and check durable state before emitting work; it should not be treated as an exact one-time scheduler. Queue delay cannot directly schedule work more than 24 hours ahead.

## Public aggregate caching

- The Cache API is available globally, but entries do not replicate outside the data center where they were created. `cache.put()` does not participate in tiered caching. Cloudflare now distinguishes this from **Workers Caching**, which caches a Worker's response before the Worker executes on a hit. Source: [Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/).
- Workers Caching honors explicit response directives and supports `stale-while-revalidate`, `stale-if-error`, cache tags, and programmatic purge. Without an explicit directive, some responses—including `200` and `404`—receive heuristic TTLs; `private` or `no-store` opts out. Source: [Workers Caching configuration](https://developers.cloudflare.com/workers/cache/configuration/).
- KV is optimized for read-heavy, highly cacheable values that change infrequently. Reads are eventually consistent: updates may take 60 seconds or longer to appear elsewhere, including after a cached negative lookup. KV has no atomic multi-operation transaction and permits at most one write per second to the same key. Sources: [How KV works](https://developers.cloudflare.com/kv/concepts/how-kv-works/) and [KV write limits](https://developers.cloudflare.com/kv/api/write-key-value-pairs/#limits-to-kv-writes-to-the-same-key).

**Suitability reading (inference, not a product choice):**

- Enabled Workers Caching, controlled by explicit cache headers, can cache an already disclosure-controlled public aggregate without creating a second persistent data model. Every participant-specific, moderation, edit, and maintainer endpoint must explicitly opt out (`private`/`no-store`) rather than rely on defaults.
- The Cache API is only a per-data-center performance cache, not a globally coherent aggregate store.
- KV can hold a materialized public snapshot only if at least 60 seconds of staleness, last-write-wins behavior, and a single controlled writer are acceptable. It is not suitable as the source of truth for submissions, edits, suppression decisions, counters requiring atomicity, or finalization state.

## Secrets and Worker-to-Worker boundaries

- Per-Worker Secrets are encrypted text bindings. `wrangler secret put` creates and immediately deploys a new Worker version; `wrangler versions secret put` creates a version without promotion. Wrangler can also declare required secret names and fail development/upload when one is missing. Source: [Workers Secrets](https://developers.cloudflare.com/workers/configuration/secrets/).
- Secrets Store is an account-level, centrally reusable secret store that remains in open beta. It currently allows one store and up to 100 production secrets per account. Values cannot be read back through the dashboard or API; a Worker uses an asynchronous binding `get()`. Deploying such a binding from CI requires Secrets Store Edit permission, and the secret scope must include `workers`. Sources: [Secrets Store overview](https://developers.cloudflare.com/secrets-store/), [limits](https://developers.cloudflare.com/secrets-store/manage-secrets/#limits), [Workers integration](https://developers.cloudflare.com/secrets-store/integrations/workers/), and [access control](https://developers.cloudflare.com/secrets-store/access-control/).
- Service bindings let one Worker call another without a public URL. Cloudflare documents no added latency or cost by default, but every call consumes a subrequest and a single incoming request can invoke at most 32 Workers. Separately deployed Workers can also experience version skew during gradual deployments. Source: [Service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/) and [service version skew](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/#version-skew-between-workers).

**Decision consequence (inference):** per-Worker Secrets cover a single-service deployment. Secrets Store adds account-level reuse and deployment-role separation but also adds a beta dependency and asynchronous reads. Service bindings provide a private seam if independent Workers are justified; they do not themselves justify splitting one small application into services.

## Admin access and fresh authentication

- A self-hosted Cloudflare Access application can protect a Worker or a specific hostname/path such as `/admin/*`. Access is deny-by-default unless a user matches an Allow policy, and a more-specific application path takes precedence over a parent path. Access checks every request for a valid application JWT before forwarding it. Sources: [Self-hosted applications and Workers](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/choose-application-type/#self-hosted-applications), [application paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/), [Access policies](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/), and [authorization cookies](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/).
- If the Worker uses the authenticated identity for authorization or audit fields, Cloudflare recommends validating the `Cf-Access-Jwt-Assertion` header at the origin rather than relying on the cookie being forwarded. Source: [Validate Access JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/).
- A short policy/application session is not necessarily fresh IdP authentication. When an application token expires but the global token remains valid, Access can issue a new application token after rechecking stored identity and policy; the IdP prompt occurs only after the global token also expires. Global duration ranges from 15 minutes to one month. Source: [Access session management](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/).
- Access independent MFA can be configured for one application or policy and set to `0m` (“Require every login” / every access), preventing reuse of a previous MFA session. However, MFA duration is evaluated only during an Access login flow and does not shorten an already-valid application session. Sources: [Enforce MFA](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/mfa-requirements/#mfa-session-duration) and [Independent MFA](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/independent-mfa/).
- Email one-time PINs are single-use and expire after 10 minutes, but they are an Access login method rather than a per-action confirmation. Temporary authentication requires an approver and grants access for up to 24 hours, so it does not provide independent approval when the only approver and operator are the same person. Sources: [One-time PIN login](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/) and [Temporary authentication](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/temporary-auth/).

**Suitability reading (inference):** Access is technically suited to the single-maintainer `/admin/*` perimeter when the policy names only the maintainer and the Worker still performs action-level authorization and CSRF protection. A distinct sensitive subpath protected as its own Access application can require fresh independent MFA at that boundary. Session duration alone cannot prove recent primary-credential entry, and the reviewed docs do not expose a transaction-level “fresh IdP authentication within N minutes” assertion for an individual POST. If that is the requirement, the application needs its own confirmation/step-up contract rather than treating a valid Access JWT as proof of freshness.

## Rate-limit enforcement boundary

- A Workers Rate Limiting binding accepts any string key and increments when the Worker calls `limit()`. Bindings with the same `namespace_id` share counters across Workers, but the only supported periods are 10 or 60 seconds. Cloudflare recommends stable user/resource identifiers rather than IP addresses, which can be shared by legitimate mobile or proxy users. Source: [Workers Rate Limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).
- Counters are separate per Cloudflare location. They are cached on the serving machine, updated asynchronously within that location, and intentionally permissive and eventually consistent. Cloudflare explicitly says the API is not an accurate accounting system. Source: [Rate Limiting locality and accuracy](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/#locality).
- D1, by contrast, serializes queries for a database and can atomically evaluate/update several statements through `batch()`. It therefore can persist an authoritative attempt ledger or counter keyed by a stable participant identifier, subject to D1 write throughput and failure handling. Sources: [D1 limits and serialization](https://developers.cloudflare.com/d1/platform/limits/#concurrency-and-throughput) and [`D1Database.batch()`](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch).

**Suitability reading (inference):** the Rate Limiting binding cannot directly express a globally exact per-number 5-minute or 10-minute rule, and composing 60-second limits does not create the same window semantics. It fits coarse abuse/load shedding where slight over-admission is acceptable. If the five- and ten-minute limits are participant-visible invariants, D1 must own the exact fixed-window or rolling-window definition and atomically record/check it before the protected side effect. The binding may still be an outer shield, but it cannot replace the D1 decision. The binding documentation does not state how supplied keys are retained, so a raw WhatsApp number should not be used as a key without a separate privacy determination; a derived stable identifier is the safer architectural boundary.

## Cron and D1 lifecycle sweeps

- Cron Triggers are expressly intended for periodic maintenance and can run as often as every minute. They use UTC, configuration changes can take up to 15 minutes to propagate, and each invocation has a 15-minute wall-time limit. Sources: [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/) and [Workers wall-time limits](https://developers.cloudflare.com/workers/platform/limits/#wall-time-limits-by-invocation-type).
- A D1 query is limited to 30 seconds, and a Cron invocation can issue 50 D1 queries on Free or 1,000 on Paid. Cloudflare directs large `UPDATE`/`DELETE` work to bounded batches rather than one mass statement. Source: [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
- Cloudflare characterizes Queues as the fit for buffering, fan-out, and simple single-step background jobs, while Workflows fit dependent multi-step processes, durable pauses, and retrying only the failed step. Queues remains at-least-once and cannot delay a message more than 24 hours. Sources: [Workers background-work guidance](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/#use-queues-and-workflows-for-async-and-background-work), [Queue delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/), and [Queue delay limits](https://developers.cloudflare.com/queues/platform/limits/).

**Suitability reading (inference):** draft expiry, closure cleanup, and 30-day unlinking are deterministic, idempotent operations against one D1 database. Cron calling D1 directly is technically sufficient while each sweep is indexed, bounded, and safely repeatable; current Cloudflare product boundaries do not by themselves justify another Queue or Workflow. The request path—not Cron—must enforce the logical deadline: reject writes after the stored close time, treat expired drafts as unavailable, and stop using a due linkage even if physical deletion awaits the next successful sweep. This makes a missed or duplicated Cron run a recoverable housekeeping delay rather than an extension of access.

A Queue becomes technically relevant if the sweep must fan out many independent chunks or trigger external side effects; a Workflow becomes relevant if closure is a durable multi-step process whose later steps depend on earlier completion or wait for human/external events. Neither product creates a documented exact wall-clock guarantee. Because the reviewed Cron docs do not fully specify failure redelivery, a hard physical-deletion deadline still requires run monitoring, an alert, and a manual rerun procedure, regardless of whether the periodic sweep is implemented inline or launches other background work.

## Observability and log boundaries

- Workers Logs stores invocation logs, custom logs, errors, and uncaught exceptions and supports filtering/querying in the dashboard. New Workers default to observability enabled, but it should still be declared in Wrangler. Structured object logs produce filterable fields; head sampling retains or drops the entire request's log context. Sources: [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) and [Workers observability best practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/#observability).
- Current retention is 3 days on Free and 7 days on Paid. A log is capped at 256 KB and is marked truncated above that. Real-time logs are not stored and may sample/drop events under high volume. Sources: [Workers Logs limits and pricing](https://developers.cloudflare.com/workers/observability/logs/workers-logs/#limits) and [Real-time logs](https://developers.cloudflare.com/workers/observability/logs/real-time-logs/).
- Workers Logpush is available on Workers Paid and can filter/sample exports, but Cloudflare now recommends OpenTelemetry export for new integrations. The native seven-day maximum means any required longer retention needs an external destination. Sources: [Workers Logpush](https://developers.cloudflare.com/workers/observability/logs/logpush/) and [OpenTelemetry export](https://developers.cloudflare.com/workers/observability/exporting-opentelemetry-data/).

**Decision consequence (inference):** platform logs are an operational signal, not an audit database. Correlation IDs and outcome/state identifiers can be logged structurally, but raw WhatsApp numbers, raw response text, secrets, and participant payloads should remain outside logs; sampling and short retention make logs insufficient as the sole evidence for consent, edits, moderation, delivery, or finalization.

## Thresholds for additional products

The following are capability thresholds from Cloudflare's product definitions, not architecture recommendations.

| Product | Cloudflare-documented fit | No docs-driven necessity when… |
| --- | --- | --- |
| Durable Objects | A globally unique, single-threaded coordination point with strongly consistent transactional storage; suited to shared live state, serialized race prevention, persistent WebSockets, per-entity state, and per-entity alarms. Sources: [What are Durable Objects?](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/) and [Rules of Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/). | HTTP handlers are stateless and relational invariants fit D1 constraints/transactions without a globally serialized in-memory coordinator or persistent connection. |
| Workflows | Durable multi-step execution with persisted step results, automatic step retries, sleeps/waits, and external-event pauses. A sleep can last up to 365 days; completed instance state is retained 3 days on Free or 30 days on Paid. Sources: [Workflows overview](https://developers.cloudflare.com/workflows/) and [Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/). | Each background unit is short and independently idempotent, and Queues plus Cron provide sufficient retry/scheduling semantics without a durable multi-step state machine or human approval wait. |
| R2 | Strongly consistent S3-compatible object/blob storage for large unstructured objects, assets, generated files, datasets, and logs. Sources: [How R2 works](https://developers.cloudflare.com/r2/how-r2-works/) and [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/). | Static files remain Worker-versioned assets, production records remain relational in D1, no user/generated files are retained, no external log archive is required, and D1's 7/30-day Time Travel window meets recovery retention. |

On the current documented product shape, none of Durable Objects, Workflows, or R2 is automatically required merely because the application uses Workers, D1, Queues, caching, or Cron. Each becomes justified only when its threshold above is an actual requirement. This is an inference from the official product boundaries, not a conclusion about requirements that the decision ticket has not yet settled.

## Explicit uncertainties to settle in the ticket

- Free versus Paid is not specified; D1 size/recovery, Queue retention, Cron count/CPU, Workers Logs retention, and Static Assets file-count limits differ materially.
- Cloudflare documents no Indonesian D1 jurisdiction. The acceptability of an `apac` location hint and Cloudflare's processing/storage geography needs an explicit privacy/legal decision.
- Expected submission write rate, aggregate read rate, database size, and burst profile are not yet supplied, so D1 headroom and the value of caching cannot be quantified.
- The required freshness of Hasil Sementara and the maximum permissible stale-on-error window are product policy, not platform facts. They determine whether response caching or a KV snapshot is safe.
- The WhatsApp provider's webhook redelivery, outbound idempotency, rate limits, signature verification, status callbacks, and data location are outside this Cloudflare-only research and still determine queue/data boundaries.
- Cron's exact failure redelivery behavior is not fully stated in the reviewed official docs; the design should not claim exactly-once execution without additional first-party confirmation.
- Required backup retention, recovery-point objective, recovery-time objective, and whether recovery must avoid overwriting production remain unspecified. These decide whether Time Travel alone suffices or an R2 export path is warranted.
- Required audit-log retention and search/export obligations remain unspecified. Native Workers Logs retains at most seven days.
- Independent release cadence, blast-radius isolation, and operator permission separation are not yet specified, so there is no evidence-based reason yet to choose one Worker versus several service-bound Workers.
